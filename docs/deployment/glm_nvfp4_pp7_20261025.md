# GLM NVFP4 with native MTP on seven heterogeneous GPUs

This change makes the Solstice GLM 5.3 Flash NVFP4 checkpoint load and serve
with native MTP4 and vision on four V100s, two RTX 3090s, and one RTX 4090.
It fixes native-draft selection, quantization correctness, load-time memory
peaks, and a bounded SM70 compact-GEMM launch failure. It does not implement
an additional DFlash2 serving mode or claim a measured speedup over MTP-free
decoding.

## Model and machine

- Checkpoint: `Solstice-AI/GLM-5.3-Flash-UNCENSORED-NVFP4-DFlash2`, revision
  `6db2f05b776babd37e4fb96a749193b3cd61993f`.
- Ubuntu 22.04, two AMD EPYC 7763 CPUs, 251 GiB host RAM.
- Four V100 32 GiB GPUs (SM70), two RTX 3090 24 GiB GPUs (SM86), and one
  RTX 4090 modified to 48 GiB (SM89). Results do not describe a stock 24 GiB
  RTX 4090.
- TP1 x PP7; physical GPU order `2,0,1,4,5,6,3`; 45 target layers split as
  `8,5,5,6,6,6,9`. Native MTP runs on the final stage, the 4090.
- Physical GPU6 is limited to 100 W and a maximum graphics clock of
  1050 MHz. Its observed temperature during the long-input check was 56 C.
- NVFP4 MoE weights use Marlin on SM86/SM89 and the SM70 backend on V100.
  Activations are FP16, KDA state is FP32, and NCCL P2P is disabled.

The model's directory name includes DFlash2 because independent GGUF draft
assets are bundled alongside the target weights. The validated deployment
uses native MTP4 from the target checkpoint. The separate DFlash2 draft
was inspected but was not loaded into the running service.

## Fixes and their scope

### Prefer native MTP metadata over repository-name heuristics

An explicit native MTP request could be changed to DFlash solely because
the checkpoint path contained `DFlash2`. Native MTP model metadata now takes
precedence over the repository-name fallback. Explicitly selected draft
families retain their existing handling. Regression cases cover names
containing DFlash, EAGLE, and EAGLE3.

### Preserve the activation clamp and independent projection scales

GLM's NVFP4 MoE requires `swiglu_limit=10`. Marlin already has a clamped
activation implementation, but backend selection and quant-config creation
did not carry this capability through. The selected backend now receives
the model's clamp value.

The checkpoint audit found different gate/up global factors in 8563 of
12384 projection pairs, with an up/gate ratio reaching approximately 10.
Collapsing both projections to the gate factor loses checkpoint information.
For Marlin, ModelOpt now preserves the two factors. GEMM uses their maximum
as a common factor, then a routed Triton pass restores the gate/up ratios
before activation and clamping. Zero factors are handled explicitly.
Independent factors are restricted to bias-free gated MoE; unsupported
combinations fail rather than silently changing the calculation.

The existing one-factor path remains unchanged when the projection factors
are equal. This avoids adding the correction launch to Qwen checkpoints
that use matching factors. The numerical check includes the extra FP16
rounding before activation; it is not a bitwise equivalence claim.

### Bound expert-weight preparation memory

Marlin repacking now consumes each expert's original contiguous packed
storage after its individual repack finishes, instead of retaining a full
list and then concatenating another full bank. The SM70 preparation path
also reuses owned storage when size and layout permit it, and preallocates
the scale banks. Padding that requires more bytes still allocates a separate
bank.

For 288 experts with a 4096 x 4096 projection, the Marlin test measured
less than 64 MiB of temporary allocation. The previous list-and-concatenate
strategy needed two additional approximately 2.25 GiB banks for this
projection. Bitwise comparisons cover the prepared weights; this memory
result does not measure the complete model's total load-time peak.

### Bound SM70 compact TP1 dispatch

The current native dispatch rejects some 40-80-group compact launches for
the GLM TP1 projections `(K,N)=(4096,4096)` and `(2048,4096)` because of its
scratch/split limit. The binding splits this restricted one-row-per-group
case into calls of at most 32 groups. It preserves expert selection and
the existing native calculation. TP4/TP8 dynamic grouped-row shapes are
excluded from this condition.

The regression uses an independent FP32 E2M1 reference and CUDA Graph
replay with changed inputs. This is a bounded binding workaround; no
CUDA/C++ extension was rebuilt for this change.

### Retain the execution policy on an excluded LM head

ModelOpt may use `UnquantizedLinearMethod` for `ParallelLMHead`. The
embedding base now captures the same execution-policy and runtime-trace
ownership information as ordinary linear layers, avoiding an attribute
error when the excluded head is applied.

## Validated serving configuration

| Setting | Value |
|---|---|
| Maximum input plus output length | 163840 tokens |
| Maximum simultaneous sequences | 1 |
| Speculation | Native MTP, 4 draft tokens |
| GPU memory utilization | 0.97 |
| Batched prefill token budget | 256 |
| Pipeline asynchronous queue depth | 4 |
| Target attention | `GLM5_SM70_SPARSE` |
| CUDA Graph mode | `FULL_DECODE_ONLY`, capture sizes 1 and 5 |
| Prefix caching | Enabled, Mamba cache mode `align` |
| Media limits | 8 images, 1 video; video functionality not tested here |

At a 0.94 memory budget, the final stage exposed approximately 0.30 GiB
for KV, below the approximately 0.90 GiB required for this single-request
window. At 0.97, the estimate was 1.73 GiB available, and startup plus
the long-input checks succeeded. The 4090 still has little free memory
under load; this does not establish headroom for additional concurrency
or arbitrary maximum-size media combinations.

The approximately 36K-token capacity originally reported by the 16K
configuration was a concurrency-equivalent value for that configuration,
not a hard single-request length limit. Fixed KDA/MTP state costs require
recomputing the capacity at the desired window and sequence count.

## Validation

The following GPU checks were run on the corresponding hardware before
the production service was brought online. Publishing the patch does not
rerun these allocations alongside the memory-filled production service.

| Targeted test file | Device / scope | Passed |
|---|---|---:|
| `tests/models/glm5next/test_mtp_config.py` | Configuration | 9 |
| `tests/quantization/test_nvfp4_marlin_clamp.py` | RTX 3090 | 17 |
| `tests/quantization/test_nvfp4_marlin_clamp.py` | RTX 4090 | 17 |
| `tests/quantization/test_nvfp4_sm70_load_memory.py` | V100 | 4 |
| `tests/quantization/test_nvfp4_sm70_compact_tp1.py` | V100 | 6 |
| `tests/model_executor/layers/test_lm_head_execution_policy.py` | LM head | 1 |

The test invocations use the matching directory's `--confcutdir`, avoiding
unrelated root test dependencies. This is 54 targeted test executions,
not a full-repository test run.

Publication cleanup adds explicit non-null assertions for type checking,
applies the repository formatter, and replaces test-only synchronization
and memory-stat calls with the equivalent `torch.accelerator` APIs.
The GPU checks above precede this cleanup; the evidence file records both
the GPU-tested and published source hashes. After cleanup, CPU regressions
passed 15 cases, with 22 CUDA-only cases skipped, and the accelerator APIs
were verified present in PyTorch 2.10.0+cu128. The publication uses the
repository's full staged-file pre-commit checks.

The running seven-GPU model passed text arithmetic, two-image color/order
recognition, and a forced tool call. Long-input requests asked for a
calibration phrase at the beginning of synthetic filler:

| Input tokens | Cached tokens | Newly computed tokens | TTFT | Result |
|---:|---:|---:|---:|---|
| 32768 | 0 | 32768 | 60.54 s | Correct phrase |
| 160000 | 26880 | 133120 | 186.83 s | Correct phrase |
| 160000, exact repeat | 152320 | 7680 | 14.50 s | Correct phrase |

Each long request produced 12 output tokens. Each recorded 12 drafted
tokens and 9 accepted tokens, with no preemptions. These tiny decode
samples demonstrate functioning speculation; they do not establish a
general acceptance rate or decode-throughput improvement. The first
160000-token request reused part of the preceding request and must not
be described as a fully uncached benchmark.

Remaining limits include first-use Triton compilation for some prefill
and vision shapes, 7680 tokens of recomputation on the exact long-prefix
repeat, untested maximum-size media combinations, and untested independent
DFlash2 GPU loading. No blanket improvement claim is made for Qwen.
